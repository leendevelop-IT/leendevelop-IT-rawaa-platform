# رَوَاء | تطوير الـ Backend: التحقق والتحليل والتنبؤ والجدولة

هذا المستند يشرح طبقة الـ Backend في النسخة المتكاملة المستقلة. تعليمات التشغيل والنشر على Render موجودة في [`README.md`](../README.md)، وإعادة تصميم الواجهة في [`UI_REDESIGN.md`](UI_REDESIGN.md).

## 1. نتيجة فحص المنصة الحالية (قبل التعديل)

| المحور | الوضع الذي وُجد | ما تم |
|---|---|---|
| البنية | FastAPI في ملف واحد `app.py` + واجهة JavaScript في `static/` (تُخدَّم على `/static`). ملفات `app.js`/`index.html`/`styles.css`… في جذر المستودع نسخ قديمة غير مستخدمة | أُبقيت كما هي؛ كل التعديلات على `static/` |
| قاعدة البيانات | SQLite افتراضيًا (`data/rawaa.sqlite3`، تُمسح على Render المجاني عند كل نشر) أو PostgreSQL عبر `DATABASE_URL`. الجداول تُنشأ بـ `CREATE IF NOT EXISTS` و`ALTER` متفرقة بلا إصدارات | ترحيلات مرقّمة `rawaa_core/migrations.py` + جدول `schema_migrations`، مختبرة على SQLite وPostgreSQL 16 وعلى ترقية قاعدة قديمة |
| الدخول والصلاحيات | PBKDF2-SHA256 (260k)، رمز جلسة مُجزّأ في قاعدة البيانات، كوكي httpOnly لمدة 24 ساعة؛ دوران: جهة رقابية ومقاول، ونطاق المقاول عبر `areas.assigned_operator` | إضافة حدّ لمحاولات الدخول الفاشلة (8 خلال 15 دقيقة → 429) وتنظيف الجلسات المنتهية؛ حماية كل الواجهات الجديدة بنفس الأدوار |
| جلب بيانات الأقمار | Statistical API بتجميع 30 يومًا (`P30D`، فسيفساء `mostRecent`)؛ القراءة لا تحمل تاريخ التقاط فعلي ولا معرّف صورة؛ الفترات تبدأ من تواريخ عشوائية لا أشهر تقويمية | قراءة لكل التقاط فعلي (`P1D`) واختيار أوضح التقاط في كل شهر، مع معرّفات المشاهد من Catalog API وعدد البكسلات ونسبة الصافي وبصمة الـ evalscript وإصدار الحدود |
| حساب المؤشرات | الصيغ صحيحة: NDVI (B08,B04)، NDMI (B08,B11)، NDRE (B8A,B05)، SAVI (L=0.5)، NDWI (B03,B08)، SI. قناع SCL يستبعد 0,1,3,6,8,9,10,11 لكن لا يستبعد الصنف 2 (الظلال) | تعريف مرجعي واحد `rawaa_core/indices.py` يولّد الـ evalscript؛ إضافة الصنف 2؛ اختبار يشغّل الـ evalscript نفسه في Node على 400 بكسل ويطابقه مع Python |
| مصدر المؤشرات المعروضة | القراءات المستوردة CSV تُخلط مع الفضائية في حساب الحالة | فصل كامل: `origin` (satellite / imported / manual / demo) و`reliability`؛ المستورد يُعرض لكنه لا يدخل في التصنيف أو التنبؤ أو التنبيه التلقائي |
| حدود الحدائق | 5 مضلعات من OSM و3 مستطيلات تقريبية (~200×150 م) حول دبوس الخريطة تشمل شوارع ومباني؛ لا مساحة محسوبة؛ الحدود يُعاد كتابتها من الكود عند كل تشغيل | تحقق هندسي، مساحة جيوديسية، حالة اعتماد وسجل إصدارات؛ الحدود المعدّلة أو المعتمدة لا يُعاد كتابتها |
| التنبيهات والمهام | التنبيه يُنشأ يدويًا فقط (زر «فحص»)؛ دورة مهمة جيدة (مفتوحة → قيد التنفيذ → بانتظار المراجعة → مغلقة) مع صورة قبل/بعد | تنبيهات تلقائية بمفتاح منع تكرار، جدولة متابعة، لقطة NDVI عند الإسناد، ملاحظات قبل/بعد، مقارنة الأثر، تقييم التدخل |
| الاختبارات والسجلات | لا توجد اختبارات ولا تسجيل للطلبات أو الأخطاء | 44 اختبارًا آليًا، سجل طلبات بمعرّف لكل طلب، تسجيل الاستثناءات، `/healthz` |

## 2. رحلة العمل المنفذة

`Satellite Data → Validation → Vegetation Analysis → Priority → Alert → Maintenance Task → Follow-up`

1. الجلب (`POST /api/areas/{id}/sync-satellite`): أوضح التقاط Sentinel-2 L2A في كل شهر داخل مضلع الحديقة.
2. التحقق: نسبة البكسلات الصافية داخل المضلع (مع تصحيح التغطية الجزئية لحافة المسار) → `reliable` ≥ 80%، `limited` 60–80%، `unreliable` أقل من 60% أو أقل من 20 بكسلًا صافيًا. وتُعرض النسبة باسم «نسبة البيانات الصالحة» لأنها لا تقيس دقة التحليل.
3. التحليل (`rawaa_core/decision.py`): القراءة الحالية والسابقة، الفرق عن المتوقع لنفس الموسم في الأعوام السابقة (أو وسيط متحرك إن لم يوجد عام سابق مع التنبيه لذلك)، اتجاه Theil–Sen لستة أشهر، استمرار التراجع عبر قراءات متتالية، موثوقية البيانات وحالة الحدود.
4. الأولوية: تدخل عاجل / تحتاج متابعة / مستقرة / بيانات غير كافية، ولا تعتمد على رقم NDVI منفرد. الموثوقية المنخفضة تخفّض «عاجل» إلى «متابعة».
5. التنبيه التلقائي: فقط عند تراجع موثوق ومن قراءات فضائية موثوقة وحدود غير مرفوضة/غير تقريبية؛ مفتاح فريد `auto:{park}:{reading date}` يمنع التكرار عند إعادة التشغيل.
6. المهمة: الجهة الرقابية تُسند التنبيه للمقاول؛ المهمة تحمل NDVI لحظة الإسناد وموعد الفحص من الجدول.
7. المتابعة: المقاول يحدّث الحالة ويوثق الصور والملاحظات قبل/بعد؛ الجهة الرقابية تغلق وتقيّم (فعّال / غير فعّال / غير محسوم) وتقارن المؤشرات قبل وبعد (`GET /api/tasks/{id}/impact`). كل خطوة في سجل الإجراءات.

التحليل لا يشخّص مرض النبات أو عطل الري؛ الإجراءات المقترحة تطلب فحصًا ميدانيًا، وعُدّلت صياغة الملخص النصي القديم من «الأرجح عطل في الري» إلى «المؤشرات تتوافق مع… ويُؤكَّد ميدانيًا».

## 3. التنبؤات وجدولة المتابعة

- التوقع (`rawaa_core/forecast.py`) بعد 7 و30 يومًا من القراءات الموثوقة فقط. يلزم 6 قراءات على الأقل وألا تكون آخر قراءة أقدم من 75 يومًا؛ وإلا لا يُعرض أي توقع.
- النماذج: آخر قراءة (مرجع)، اتجاه Theil–Sen مخمّد، Holt مخمّد، نفس الموسم من العام الماضي + الانحراف الحالي.
- Backtesting متدحرج على آخر 8 قراءات (كل توقع يستخدم الماضي فقط، وهذا مختبر آليًا)، ويُختار نموذج فقط إذا تفوّق على المرجع.
- عدم اليقين: نطاقا 80% و95% من أخطاء الـ backtest نفسها، يتسعان مع الأفق.
- احتمال استمرار التراجع يظهر فقط إذا تفوّق النموذج على المرجع وكان السجل ≥ 8 قراءات والاتجاه تراجعًا.
- كل توقع يُحفظ في `predictions` ويُقارن تلقائيًا بالقراءة الفعلية عند وصولها (دقة حية: `GET /api/forecast-accuracy`).
- الجدولة (`rawaa_core/scheduler.py`): عاجل 3 أيام، متابعة 14 (7 إذا رجّح التوقع استمرار التراجع ≥ 60%)، مستقرة 30 (14 إذا كان خطر التراجع ≥ 50%)، بيانات غير كافية 7 لمراجعة البيانات والحدود. إعادة التقييم بعد الفحص بعشرة أيام (ممرّان لـ Sentinel-2). مفتاح `(park, cycle_key)` فريد → لا تكرار.

## 5. الواجهة

> في هذه المرحلة أُضيفت العناصر التالية بأسلوب المنصة الحالي؛ ثم أُعيد تصميم صفحتي «تفاصيل الحديقة» و«التنبؤات وجدولة المتابعة» لاحقًا (انظر `docs/UI_REDESIGN.md`). بقية الصفحات لم يُعَد تصميمها.

- عنصر جديد في القائمة الجانبية: «التنبؤات وجدولة المتابعة | Predictions & Monitoring Schedule» بنفس البطاقات والجداول والشارات، مع فصل بصري بين «قراءة فعلية» و«توقع».
- صفحة الحديقة: بطاقة «ملخص القرار» وبطاقة «حدود الحديقة» (اعتماد/رفض/تعديل) وسجل القراءات ومصدر كل قراءة.
- المهام: زر «أثر التدخل» وتقييمه، وحقول ملاحظات قبل/بعد في نموذج الإنجاز.
- التقارير: أزرار التصدير الجديدة. العربية/الإنجليزية والوضع الداكن/الفاتح مدعومة.
- إصلاح صغير: منع بناء الخريطة مرتين عند إعادة الرسم السريع (`Map container is already initialized`).

## 6. ما يحتاج مفاتيح أو تهيئة خارجية

| المتطلب | لماذا | أين |
|---|---|---|
| `COPERNICUS_CLIENT_ID` / `COPERNICUS_CLIENT_SECRET` | جلب القراءات الفعلية. بدونهما لا تُختلق أي قراءة؛ الحدائق تظهر «بيانات غير كافية» | Render → Environment (موجودان في `render.yaml` كـ `sync:false`) |
| `DATABASE_URL` (PostgreSQL مثل Neon) | Render المجاني يمسح SQLite عند كل نشر/إعادة تشغيل | Render → Environment |
| `RAWAA_AUTO_PIPELINE=1` (اختياري) و`RAWAA_PIPELINE_HOURS` | تشغيل التحليل دوريًا داخل الخادم. بديل مضمون التوقيت: Render Cron Job (مدفوع) يشغّل `python scripts/run_pipeline.py` | Render → Environment |
| اعتماد الحدود | لا يمكن آليًا؛ رسم الحدائق الثلاث التقريبية من مخطط الأمانة ثم اعتماد الثماني | الواجهة: صفحة الحديقة → حدود الحديقة |
| كلمات مرور الحسابات التجريبية | `Rawaa2026!` منشورة في الواجهة؛ مقبول للعرض لا لبيانات حقيقية | قرار منفصل قبل الاستخدام الرسمي |

ملاحظة: مسارات Copernicus الجديدة (`/statistics/v1`, `/catalog/v1/search`) مستخدمة؛ القديمة ما زالت تعمل لكنها ستُوقف لاحقًا.

## 7. الاختبارات ونتائجها

```
pip install -r requirements-dev.txt
pytest                                   # SQLite مؤقتة
RAWAA_TEST_DATABASE_URL=postgresql://…  pytest   # قاعدة PostgreSQL مؤقتة (تُمسح!)
```

النتيجة: **44/44 ناجحة على SQLite و44/44 على PostgreSQL 16.** تغطي: صيغ المؤشرات ومطابقة الـ evalscript في Node، أقنعة السحب والظلال، تصنيف الموثوقية، صلاحية المضلعات ومساحاتها، اختيار أوضح التقاط شهري ومعرّفات المشاهد، تصنيف الأولوية بكل حالاته، التوقع والـ backtesting وعدم استخدام بيانات المستقبل، الجدولة، التنبيه التلقائي ومنع التكرار بعد إعادة التشغيل، الإسناد ودورة المهمة والتقييم، الصلاحيات وحد محاولات الدخول، التقارير، المزامنة عبر Copernicus مُحاكاة.

تحقق إضافي يدوي: ترقية قاعدة بيانات أُنشئت بالنسخة الحالية من `main` (قراءات Copernicus قديمة + CSV) على SQLite وPostgreSQL: الترحيلات طُبّقت، والقراءات القديمة صُنّفت `satellite / rawaa-s2-v1` والمستوردة `imported / unverified`، ولوحة التحكم تعمل. وفُحصت كل صفحات الواجهة في Chrome (عربي/إنجليزي، داكن/فاتح، جهة رقابية/مقاول) دون أخطاء JavaScript.

## 8. النشر، وربط قاعدة بيانات موجودة

خطوات النشر على خدمة Render جديدة موجودة في [`README.md`](../README.md).

إذا أردتم لاحقًا تشغيل هذه النسخة على قاعدة بيانات المنصة الحالية (للاحتفاظ بقراءاتها ومهامها):

1. **نسخة احتياطية** أولًا (في Neon: فرع/snapshot)، ثم اربطوا `DATABASE_URL` بنسخة من القاعدة (فرع Neon)، لا بالقاعدة الأصلية مباشرة.
2. الترحيلات تعمل تلقائيًا عند الإقلاع، وهي إضافية فقط (أعمدة وجداول جديدة) ولا تحذف بيانات. القراءات القديمة تُصنَّف `satellite / rawaa-s2-v1` والمستوردة `imported / unverified` (مُختبر على SQLite وPostgreSQL).
3. لا تشغّلوا النسخة القديمة والجديدة على القاعدة نفسها في الوقت ذاته: النسخة القديمة تعيد كتابة حدود الحدائق من الكود عند كل تشغيل، فتضيع تعديلات الحدود واعتمادها.
4. بعد الربط: `GET /healthz` يُظهر `schema_version: 5` ← مزامنة حديقة واحدة ← مراجعة سجل القراءات ومعرّفات المشاهد ← تشغيل التحليل.
